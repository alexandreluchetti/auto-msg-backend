# ADR-002 — Hybrid conversation engine: deterministic flows + LLM with tools

- **Status:** Accepted, refined by [ADR-011](ADR-011-humanized-service.md) (free conversation by default; flows in YAML dropped; interactive messages chosen by the response composer)
- **Date:** 2026-10-28

## Context

Customers write freely ("me vê duas calabresa e uma coca de 2l, entrega no centro"), but parts
of the service must be exact: price, total, address, payment method and order confirmation. A
bot mistake there costs money and trust.

## Decision

A layered pipeline, in this order, on every turn:

1. **Deterministic guards** (LGPD, opt-out, privacy notice, conversation in `HUMAN`, opening
   hours). They never go through the LLM.
2. **Flow runtime**: declarative flows (YAML) as state machines with slots. Structured answers
   (button/list id) move the flow forward without the LLM.
3. **LLM with tool calling** for free text:
   - **Read** tools (menu, opening hours, delivery fee, order status) are the only source of
     business facts.
   - **Draft** tools (add/remove a cart item, set the address) change only the conversation
     state.
   - **Control** tools (`start_checkout`, `request_human`) hand control to a deterministic
     flow or to a human.
   - **No tool confirms an order.** Confirmation is a step of the checkout flow: a summary
     generated by code from the database + a "Confirm" button. Only the click creates the order.
4. **Rendering**: buttons/lists built by code from tool results; the LLM writes the text
   around them.

Safeguards: a limit of tool iterations per turn; input validation of every tool against its
schema; scope guard (business subjects only); if the LLM fails or refuses, a default answer +
an offer of an attendant; N misunderstandings in a row → handoff.

Conversation state (`conversation.context` JSONB): active flow, filled slots, cart, counters.
History sent to the LLM is limited to the latest messages + a summary of the state.

## Alternatives considered

| Alternative | Why not |
|---|---|
| **Flows/menus only** (decision tree) | Predictable, but frustrates people who write freely; a lot of maintenance per tenant. |
| **LLM only ("free agent")** | Flexible, but hard to guarantee correct prices/totals and explicit confirmation; less testable behavior. |
| **Classic NLU (intents + entities)** | Needs training per segment; an LLM with tools covers the same with less effort. |

## Consequences

- (+) Critical parts are testable with ordinary unit tests; the LLM stays where it adds value.
- (+) Flows and tools belong to the Segment Pack → reuse across tenants of the same segment.
- (−) Two kinds of behavior to keep consistent (flow ↔ LLM transitions).
- (−) Needs an evaluation set (evals) with real conversations to evolve prompts without
  regressions — planned for M5.
